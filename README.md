# XenoDLLRE

Static reverse engineering of **Xeno v1.3.65**, a Roblox script executor, with detection tooling built from the results. The goal is to document how the executor works and what it leaves behind, for defensive and anti-cheat use. This repository does not contain or improve executor functionality.

## Summary

Xeno is a native x64 DLL (`Xeno.dll`) driven by an Electron UI. It does not load a DLL or create a thread in Roblox. Instead it opens the Roblox process from outside, allocates and writes memory in it with `VirtualAllocEx`/`WriteProcessMemory`, and so **replaces the bytecode of the en-us locale translation ModuleScript** under `RobloxGui.Modules`. Roblox then runs Xeno's client script when that module loads. The client then talks to a **localhost HTTP server** in the DLL, runs user scripts by having the DLL write compiled Luau bytecode into ModuleScripts it repeatedly `require()`s, and leaves distinctive objects in `CoreGui`.

The client script and a copy of Roblox's en-us table are embedded as resources protected by a **32-byte repeating XOR key over zstd**. The key was recovered from a CRT initializer and independently confirmed by known plaintext, and both resources were decrypted. On every attach the client also downloads and runs `code.lua` from the developer's host, which lets the developer push arbitrary code into every attached session without shipping a new DLL.

All of this is static analysis. Nothing was executed. Each claim in [`docs/research/FINDINGS.md`](docs/research/FINDINGS.md) carries an evidence reference and a confidence level.

## Key results

| | Result | Confidence |
|---|---|---|
| Attach | Bytecode replacement of the en-us translation ModuleScript (F-30) via `VirtualAllocEx` + `WriteProcessMemory`, no suspension, no remote thread (F-31) | Strongly supported (target) / Confirmed (write path) |
| Execution | Local `require()` loop on random-named ModuleScripts; DLL compiles, writes and verifies bytecode on a detached thread per `Execute` call (F-13, F-40, F-41) | Confirmed |
| Offsets | Per-Roblox-version offsets fetched from a pastebin URL at each attach, `x3no.pages.dev/ep.zst.enc` as fallback (F-33, F-34) | Confirmed (code) |
| Protocol | `POST /f?e=<0-21>` plus `/ls`, `/rq`, `/qt`, `/cb` on localhost (F-51, F-52) | Confirmed (client) |
| Resources | XOR key `3EFD5045…A92AF5BB` + zstd; unchanged from v1.3.40 (F-60, F-61) | Confirmed |
| Remote code | `code.lua` fetched and executed on every attach (F-63) | Confirmed (client) |
| Signing | Self-signed `CN=Rizve A` Authenticode certificate, renewed yearly with a new serial, Sectigo timestamp; usable as a detection indicator (F-04) | Confirmed |
| Identifier leakage | Script HTTP requests send the user's HWID (`exploit-guid`, `xeno-fingerprint`) and current game server to any host (F-54) | Confirmed (client) |
| Artifacts | `CoreGui/<pid>` folder with `Message` "DO NOT DELETE: BELONGS TO XENO", `shared.__Xeno` (F-70, F-71) | Confirmed |
| Platform vulnerability | None established ([`docs/DISCLOSURE.md`](docs/DISCLOSURE.md)) | — |

## Usage

Samples are not included. To reproduce the analysis, obtain the Xeno installer yourself, work inside an isolated VM, and never run the installer or DLL on a machine you care about.

```bash
pip install pefile zstandard yara-python capstone   # 7-Zip is also required for update_sample.py

python tools/update_sample.py app/Xeno-v1.3.65.exe     # → sample/TEST.dll, reports/SAMPLE_REPORT.md
python tools/decrypt_resources.py sample/TEST.dll payloads/
python detection/xeno_detector.py sample/TEST.dll -v
python tools/compare_samples.py sample/TEST-v1.3.40.dll sample/TEST.dll

python tools/xrefs.py sample/TEST.dll --string "Intercepted translation module" --callers 2

python -m unittest discover -s tests -v                # sample tests skip when samples are absent
```

Without samples you can still read the documentation, run the tests, and use the detector and YARA rules on your own files.

Suggested reading order: [`BRIEFING.md`](BRIEFING.md), then [`THREAT_ASSESSMENT.md`](docs/defense/THREAT_ASSESSMENT.md) and [`COUNTERMEASURES.md`](docs/defense/COUNTERMEASURES.md) for the defensive picture, or [`FINDINGS.md`](docs/research/FINDINGS.md) and [`ARCHITECTURE.md`](docs/research/ARCHITECTURE.md) for the technical detail. [`METHODOLOGY.md`](docs/research/METHODOLOGY.md), [`DETECTION.md`](docs/defense/DETECTION.md), [`LIMITATIONS.md`](docs/research/LIMITATIONS.md) and [`DISCLOSURE.md`](docs/DISCLOSURE.md) complete the set.

## Status

- Static analysis of v1.3.65 complete for exports, resources, client script and protocol. The internal attach, execution, watcher, offsets and Discord code paths were mapped by cross-reference on 2026-11-10, which corrected several earlier inferences (see the corrections log in [`FINDINGS.md`](docs/research/FINDINGS.md)).
- Disassembly, imports, strings and signature re-verified against both real samples on 2026-11-10. [`SAMPLE_REPORT.md`](reports/SAMPLE_REPORT.md) and [`COMPARE_REPORT.md`](reports/COMPARE_REPORT.md) were regenerated.
- Detection tools tested on both real builds (pinned by `tests/test_samples.py`) and on synthetic fixtures; no benign-corpus validation yet.
- Open questions are listed at the end of [`docs/research/FINDINGS.md`](docs/research/FINDINGS.md). The main one, the script identity of the hijacked module, cannot be settled by static analysis.
